# Create a presentation

This workflow is for an author or an agent working in a clone. Read the root
[agent instructions](../AGENTS.md). Studio is the default; Academic is available
for conventional Beamer authoring. Both use the existing shared themes and icons.

## 1. Start a private project

Install [Python and a compiler backend](SETUP.md), then run from the repository root:

```sh
python3 scripts/deck.py new my-talk
python3 scripts/deck.py layouts
```

On Windows use `py -3` instead of `python3`. For Academic:
`python3 scripts/deck.py new my-talk --style academic`.
Names must be portable lowercase kebab-case. Existing folders are never overwritten.

```text
presentations/my-talk/
  main.tex          editable presentation
  brief.md          requirements, sources, assumptions and verification
  assets/           images and other deck-specific inputs
  references.bib    verified references for this deck
build/presentations/my-talk/
  main.pdf          compiled deck and its independent latexmk cache
  main.log          final compiler log
  check.json        technical findings; not visual approval
  preview/          numbered PNG pages, generated by check --preview
```

Personal projects and their outputs are ignored by Git and excluded from library
link checks and distribution packages. Only `presentations/README.md` is tracked.
Back up or share your deck deliberately: Git does not protect these ignored files.
Normal builds never delete a deck; `make clean` removes all `build/` outputs,
including these PDFs, but keeps sources and stable releases in `dist/`.

## 2. Turn a brief into slides

Read and complete `brief.md` before writing: goal, audience, duration, language,
real author/institute, supplied sources, outline and assumptions. Ask only for
missing information that prevents an honest or useful presentation. A provisional
outline does not need an approval round unless the user asks for one.

Use English by default. Explicit requests for another deck language take priority;
repository guides, comments and official examples stay in English. Never invent
names, evidence, statistics, sources or results. Cite supplied or verified sources,
and label hypothetical numbers as illustrative.

The Studio starter follows **cover → team → contents → content → closing**.
The title page is classic blue. The team page is optional; check and replace its
example figures, labels and graphics instead of presenting them as current facts.
The final QR is enabled by default; check its intended destination or supply a
custom QR. See [team](STUDIO-TEAM.md), [title and contents](STUDIO.md), and
[closing options](STUDIO-CLOSING.md). Academic retains its own standard pages.

## 3. Choose a composition and replace its fields

```sh
python3 scripts/deck.py layouts
python3 scripts/deck.py layouts --model icon-cards
python3 scripts/deck.py layouts --model icon-cards --json
python3 scripts/deck.py layouts --all
```

Start with featured models. The [grouped gallery](templates/index.html) and
[individual model guides](STUDIO-MODELS.md) show alternatives. Each variant has its
own supported palettes and fields; do not assume every layout has a light/blue pair.
`--json` reports the actual field defaults, types, boxes, source and options.
Some compatibility names are source-composition IDs; prefer grouped model IDs.

```latex
\studiotemplate[
  variant=three,
  title={Three useful roles},
  caption-one={People},
  caption-two={Processes},
  caption-three={Tools},
  graphic-one={\alice[height=1cm]},
  graphic-two={\cow[height=1cm]},
  graphic-three={\asset[height=1cm]{coin}}
]{icon-cards}
```

Consult the specific variant's fields before copying a command. Use
`\studioframe{A concise heading}{...}` for simple content; normal Beamer frames are
also supported. Each template creates its own frame: do not wrap it in another.
The [icon guide](ICONS.md) covers all shortcuts, sizing and fixed artwork colours.

Keep Inter, the documented palette, geometry and visual hierarchy. Replace every
relevant text, caption, diagram label, graphic and credit explicitly. Empty fields
keep their space. If content overflows, shorten it, split the slide or choose a
better model. Do not reduce font sizes or edit shared layouts during deck creation.
Complex code/data may be supplied through local files where the model supports them.

## 4. Keep paths and sources local

Compilation always runs from the repository root. The scaffold configures its own
image search path, so a local image can be used as follows:

```latex
\includegraphics[width=3cm]{example.pdf} % presentations/my-talk/assets/example.pdf
\input{presentations/my-talk/sections/introduction.tex}
```

Use the full repository-relative path for `\input` and file-based template fields;
LaTeX does not change directory when reading an included file. Keep new files within
this deck, and never reference another personal project. Shared `\asset` commands
continue to find prepared library artwork without copying it.

The scaffold includes commented bibliography setup. Uncomment both lines when
needed, add verified BibLaTeX entries, cite them and print the bibliography:

```latex
% In the preamble:
\usepackage[backend=biber,style=numeric]{biblatex}
\addbibresource{presentations/my-talk/references.bib}
% In the document:
\studioframe{Sources}{\printbibliography}
```

Use `\cite{key}` beside the claim it supports. Biber runs through latexmk; do not
copy `.bbl` or auxiliary files between presentations.

## 5. Build, check and inspect every page

```sh
python3 scripts/deck.py build my-talk --open
python3 scripts/deck.py check my-talk --preview
# Alternative with TeX Live/MacTeX installed:
python3 scripts/deck.py check my-talk --backend native --preview
```

Docker is the default. Its image is prepared on the first build and reused.
The native backend never starts Docker. Both use the same existing build launcher,
with separate PDF/auxiliary/cache directories for each deck. `--force` requests a
full latexmk rebuild; it does not regenerate artwork or catalogues.

`check` inspects the final log for errors, overflow, missing glyphs and unresolved
citations/references. It warns about common placeholders and built-in team content;
this is a heuristic, so inspect the source and **all visible content** yourself.
Technical errors return a nonzero exit code. Placeholder warnings do not prevent
an intentionally unfinished draft from compiling. A failed build marks the report
failed even if an older PDF still exists.

PDF page/font inspection and PNG previews use Poppler locally or in Docker.
Without Poppler, native compilation still works; `check` records skipped PDF
inspection, and an explicit `--preview` request fails with installation guidance.
Linux: `poppler-utils`; macOS: `brew install poppler`; Windows: a Poppler package
such as `conda install -c conda-forge poppler`. No SVG converters or shell escape
are needed for ordinary authoring.

Inspect every numbered PNG or PDF page. Check title/logo clearance, alignment,
line breaks, readability, contrast, image cropping, labels, spelling and credits.
Rendering is not graphic approval. Record the pages inspected, source verification,
technical report and any unavailable checks in `brief.md`, then deliver the PDF,
editable source and report paths. Never claim visual inspection you did not perform.

## Scope and maintenance

Ordinary authoring changes only the current project and its output. Do not run
catalogue sync, approve library models, replace releases, commit, push or publish
unless specifically asked. A shared-layout problem should be reported as library
maintenance, with a concrete example, rather than silently changing every deck.

Use [repository structure](STRUCTURE.md), [maintenance](MAINTENANCE.md), and
[contributing](../.github/CONTRIBUTING.md) for work on the library itself.
